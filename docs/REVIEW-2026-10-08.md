# deeebian — Review of the Eee PC 701 image and the Hermes pushes

**Date:** 2026-10-08
**Reviewer:** Hermes (m5-7)
**Scope:** `GodSpoon/deeebian` (primary) and `GodSpoon/eeepc701-linux` (overlap), the shipped
`v1.0.0` image, the unmerged `support-report-script` branch, and the physical flash to the
internal SD reader.

**Verdict:** the image is real, boots, and is a solid baseline — but it is **not** yet an
excellent 701 image. There are **two public repos with diverging `v1.0.0` releases**, **three
verified false claims in the docs**, a **missing console framebuffer**, a **webcam driver that
is not actually built in**, and **no wifi bring-up safety net** for the one failure we have
already hit on this exact hardware. All of that is fixable in source; details below.

---

## 1. Repo overlap — two repos, two different `v1.0.0` releases

| | `GodSpoon/eeepc701-linux` | `GodSpoon/deeebian` |
|---|---|---|
| Created | 2026-10-06 20:54Z | 2026-10-06 (continuation) |
| Default branch | `master` | `main` |
| Commits | 4 | 10 |
| CI workflow | **none** | `.github/workflows/build-image.yml` |
| Released `v1.0.0` | 2026-10-06 20:58Z | 2026-10-06 22:37Z |
| Asset size | 639,009,480 B | 619,431,428 B |
| Asset sha256 | `f5a6f0b2f9d1…b944a9` | `90a05368672a…4dfa0` |

Both are **public** and **neither is archived**. The `eeepc701-linux` repo was rebranded to
"Deeebian" in commit `c6acd30` (2026-10-07 02:07Z) — a rebrand that **exists only in that repo**.

**The hazard is concrete:** the two `v1.0.0` releases are *different images under the same
version number*. A user who downloads "v1.0.0" from the old repo gets a different, older,
non-CI-reproducible build than one who downloads from `deeebian`. Version numbers are supposed
to be immutable identifiers; here one tag means two artifacts.

**Recommendation:** make `deeebian` the single source of truth. Either archive
`eeepc701-linux` (GitHub: Settings → Archive) or replace its README with a one-screen pointer
to `deeebian`, and delete or re-tag its `v1.0.0` release so the tag is not ambiguous. Do not
reuse `v1.0.0` on `deeebian` for a rebuild — cut `v1.1.0`.

> Note: GitHub repo *visibility* is per-repo, but *version tags* are per-repo too. Two repos
> cannot share one authoritative `v1.0.0`. This is the same class of problem as publishing to
> two places and calling them the same artifact.

### Repos checked and cleared of overlap

The account has one other Debian image repository, `GodSpoon/debian-iso-builder`. It was checked

## 3. Verified problems in the shipped `v1.0.0`

Downloaded the release, checked the sha256 against the sidecar (match), unpacked it, and read
the kernel config and rootfs directly.

### 3.1 The docs claim a webcam that is not there — **false claim**

`README.md` and `docs/report.html` both list:

```
| Webcam | uvcvideo | works |
```

Reality in `/boot/config-6.12.112-eeepc`:

```
# CONFIG_MEDIA_SUPPORT is not set
```

`CONFIG_MEDIA_SUPPORT is not set` means the entire media subsystem is compiled out. There is no
`uvcvideo`, not built-in and not as a module (`find /lib/modules/*/ -name 'uvcvideo*'` → empty).
**The webcam does not work on this image.** Either build it in or delete the claim.

### 3.2 No framebuffer console — the text console disappears mid-boot

```
CONFIG_VGA_CONSOLE=y
# CONFIG_FRAMEBUFFER_CONSOLE is not set
# CONFIG_FB_VESA is not set
# CONFIG_FB_EFI is not set
# CONFIG_DRM_FBDEV_EMULATION is not set
CONFIG_DRM_I915=y
```

Only the legacy VGA text console exists, and `i915` is built in with **no fbdev emulation**.
When i915 takes over the display, nothing re-registers a console. The practical effects on real
hardware:

- Console output stops at the point DRM initialises — this is exactly what the QEMU boot showed:
  readable boot text at 25 s (the screenshot above), then a black screen at 50 s.
- **No virtual terminals** (Ctrl+Alt+F1…F6) under the graphical session — the single most useful
  escape hatch on a machine like this is gone.
- No kernel messages after early boot, so a hardware failure on the real 701 is much harder to
  diagnose — which is the *opposite* of what an exploratory baseline wants.

Fix: `CONFIG_FRAMEBUFFER_CONSOLE=y` + `CONFIG_DRM_FBDEV_EMULATION=y` (this gives the DRM
framebuffer console, which is the modern path), and `CONFIG_FB_VESA=y` as a belt-and-braces
early console. This is a real bug, not a preference.

### 3.3 `CONFIG_HZ=1000` on a 900 MHz netbook

```
CONFIG_HZ_1000=y
CONFIG_HZ=1000
```

A 1000 Hz tick wakes the CPU 1000×/s for no benefit on a 900 MHz Celeron M whose whole reason
for existing is battery life. `CONFIG_HZ_250` (or 100) is the standard netbook choice. The
config-edit list in `scripts/20-kernel.sh` never touches `HZ`, so it silently inherited the
`i386_defconfig` default.

### 3.4 No wifi bring-up safety net — the failure we have *already hit*

The prior Alpine attempt on this same 701 **booted to a shell with no network**, and the
diagnosis recorded at the time was that the AR5007EG radio is soft-blocked or ACPI-powered-down
at boot until poked:

```sh
echo 1 > /sys/devices/platform/eeepc/wlan
rfkill unblock all
```

`deeebian` ships `systemd-rfkill` and relies on NetworkManager, but there is **no explicit
unblock step** in `30-configure.sh`, no `local.d`, no unit that pokes the eeepc platform device.
Given that this is the one hardware interaction we have already seen fail on this exact machine,
shipping without a safety net is the highest-risk omission in the image. It also costs nothing:
a tiny oneshot unit that runs `rfkill unblock all` and writes the sysfs node before
`NetworkManager.service` is strictly better than hoping.

### 3.5 The monitoring path is broken as shipped — and the script is not in the image

`scripts/deeebian-report.sh` — the on-device diagnostics collector written by the Hermes prod
push (commit `738f5f6`, 2026-10-07) — is **not in the image** and **not merged to `main`**: it
lives only on the unmerged branch `origin/support-report-script`, which is 1 commit ahead of
`main` and touches nothing else.

Its upload targets are also dead:

```sh
TARGETS="sam@192.168.70.130 sam@hermes-prod.nb.rip"
```

- `hermes-prod.nb.rip` → **NXDOMAIN**, does not resolve.
- `192.168.70.130` → no response (that is the rack/homelab subnet `192.168.70.x`; this machine
  reaches the homelab over NetBird as `pve` at `100.69.56.74`, which *does* respond).

So "the monitoring path" does not currently work end-to-end: the collector is unmerged, absent
from the flashed card, and pointed at a hostname that does not exist.

### 3.6 Committed build-debug logs

`.ciwatch.log`, `.ciwatch6.log`, `.ciwatch7.log` (18 KB, 14 KB, 13 KB of CI watcher output) are
**tracked in the repo** and were committed into unrelated commits. They are not in `.gitignore`.
Noise, but it clutters diffs and misleads anyone reading history.

### 3.7 Stale deliverable paths in the report

`docs/report.html` lists the deliverables as `~/workspace/eeepc701/scripts/` on hermes-prod and
`pve-r630:/var/lib/vz/eeepc/`. Neither is the source of truth any more — the repo is. Anyone
following the report to find the scripts will look in the wrong place.

### 3.8 The rebrand was never carried forward

`eeepc701-linux`'s `c6acd30` renamed things to "Deeebian". That commit is **not** in `deeebian`,
so the shipped image still presents as the old name:

- `scripts/40-image.sh` → GRUB entries read `"EeePC Linux (kernel …)"`, not `"Deeebian"`.
- `scripts/30-configure.sh` → `/etc/motd` reads `EeePC 701 Linux — Debian 12 …`.
- `docs/index.html` → `<title>EeePC 701 Linux</title>`.

Cosmetic, but it means the primary repo is *behind* the abandoned one on branding, which is
exactly backwards.

## 4. Test-plan problem: the target card cannot work in a 701

The card this was flashed to is **494.9 GB** — an **SDXC** card (SD 3.0, exFAT-class, >32 GB).

The Eee PC 701's internal reader is an SD/SDHC-class, USB-attached reader, and the 701 is
documented as **unable to use SDXC cards** — the practical limit is a **≤32 GB SDHC card**.
Independent sources agree, and this is a well-known 701 limitation. Two consequences:

1. The card we just flashed **will very likely not be recognised by the 701's internal reader**
   at all, so the "flash it and test on the Eee PC" plan needs a ≤32 GB SDHC card to actually
   be a test.
2. Even if it were recognised, `expand-root.sh` would grow the root filesystem to **~460 GB** —
   pointless, and it turns every `fsck`/`resize2fs` on a 900 MHz Celeron M into a long operation
   for a device that will never use the space.

The flash itself is verified good: `dd` wrote **7,516,192,768 bytes = exactly the raw image
size** in 150.7 s (49.9 MB/s), and the card ejected cleanly. The image on the card is correct;
the *card* is the wrong class for the target.

## 5. Other observations (minor, no action required)

- **512 MB stock RAM.** The image is tuned for 2 GB (`zram` 1 GB, `swappiness=150`, earlyoom at
  default with `-r 3600`). A stock 512 MB 701 will be tight at the Openbox desktop — Netsurf is
  the pleasant path, Firefox ESR will thrash. Worth stating in the README rather than implying
  2 GB is the baseline.
- **`intel-microcode` installed**; the Celeron M ULV 353 (Dothan) is covered by Intel microcode,
  so this is harmless and probably mildly useful.
- **No `systemd-networkd` fallback** — NetworkManager only. Fine, but it means a NetworkManager
  failure is a total network failure; the rfkill safety net in §3.4 matters more because of it.
- **~4.7 GB of the 7 GiB image is empty** (rootfs is 2.4 GB of a 7167 MiB partition). Harmless on
  a 32 GB SDHC; worth knowing that the "7 GiB" is mostly headroom.
