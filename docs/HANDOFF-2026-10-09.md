# deeebian — handoff / current state

**As of 2026-10-09.** Read this first in a new session. Everything below is either *verified on
real hardware* or explicitly marked as *not verified*. Claims are separated on purpose — do not
promote an unverified item to fact.

Repo: `https://github.com/GodSpoon/deeebian` (public). Branch of record for current work:
**`v1.3.0`** → **PR #3** (open).

## 0. TL;DR and the one open problem

The image is in good shape and the tooling around it grew a lot today. **The open problem is that
the Eee PC 701 is currently not booting after a reboot**, and we do not yet know why. The SD card's
filesystem was verified intact immediately before that reboot, so this is very likely recoverable
— see §5 for the diagnosis and §6 for recovery options. **Do not touch `/dev/sda` again until §5
is understood.**

## 3. Key gotchas (each cost real time; do not relearn these)

- **`sources.debian.org` / `packages.debian.org` report against amd64.** A query for an i386-only
  question returns a confident false "MISSING" — a subagent reported `tlp: MISSING` for bookworm
  i386; it is present (`1.5.0-2`). Use
  `curl -s .../bookworm/main/binary-i386/Packages.gz | gzip -dc | grep -A3 '^Package: <n>$'`,
  or the build log's own `Setting up <pkg> ...`.
- **A `workflow_dispatch` release tags the WRONG commit.** With `release_tag:` set, the build runs
  from the dispatched branch but the tag lands on the **default branch HEAD** — so `v1.1.0` and
  `v1.2.0` both resolve to the same old `main` commit while the images genuinely differ.
  Verify `git rev-list -n1 <tag>` == `gh run view <run-id> --json headSha`. **This is still
  unfixed** — see §7.
- **First-boot `systemd-analyze` is not the machine's boot time.** 51 s of it is `ssh-keygen -A`
  (0.18 s thereafter) and 19.7 s is `expand-root`. Reboot once before quoting a number, and never
  "optimise" the keygen away — that would ship a fixed host key and break clone-safety.
- **`sudo` driven by expect must print a prompt.** `sudo -S -p ''` suppresses it and the expect
  hangs until timeout with no output, looking like a dead host. Use
  `sudo -S -p SUDOPROMPT:` and match on that.
- **A non-root user cannot read `/root` over ssh** — `scp user@host:/root/file` fails with
  "No such file or directory" (0700 dir). Stage to the user's home, then scp.
- **A changed SSH host key after (re)flashing is expected, not an attack.** The image regenerates
  host keys per install. Confirm it is the same machine, `ssh-keygen -R <host>`, reconnect.
- **Long remote jobs must be detached** (`setsid nohup … </dev/null >/dev/null 2>&1 &`). An SSH
  timeout kills the session and, with it, the job — this silently aborted a backup and an SSD write.
- **Verify a raw-device backup with FAST checks.** On 900 MHz, `gzip -dc img.gz | wc -c` outlives
  any timeout. `gzip -l` (trailer), the live-vs-backup first-512 B partition table, and a first
  32 MiB md5 prove the same thing.
- **Don't put a multi-GB `sha256sum` in a critical path.** Hashing the 1.3 GB backup before a write
  burned the whole command timeout. Verify separately, or not on the hot path.
- **Backtick "comments" inside a `\`-continued shell command are executed as subshells.** Write one
  call per group instead.
- **Function definitions must precede any use.** `--auto` failed with `say: command not found`
  (rc=127) because the argument-parsing block was inserted above the `say`/`die`/`run` definitions.
  `--dry-run` hid it (that branch only sets a variable). **Only running it for real surfaced this.**

## 4. Corrections made today (each was a documented claim the hardware disproved)

1. **SDXC works.** README/MOTD/REVIEW claimed a ≤32 GB SDHC ceiling. False — the v1.2.0 image
   boots from a **128 GB SDXC** in the 701's own reader (`244277248` × 512 B ≈ 116 GiB, root grown
   to 115 GB). Corrected, with the old reasoning kept as a marked-superseded record.
2. **zram ran the wrong algorithm, silently.** The unit did
   `echo lz4 > comp_algorithm 2>/dev/null || true`. This kernel does not build the LZ4 zram
   backend (`CONFIG_ZRAM_BACKEND_FORCE_LZO=y`, `ZRAM_DEF_COMP="lzo-rle"`), so the write failed and
   `|| true` hid it — the machine ran `lzo-rle` while source, README and MOTD all said `lz4`.
   Now picks lz4 only if offered, else an **explicit, logged** fallback.
3. **`ssh.service`'s 51 s is first-boot-only** (measured both ways) — not a recurring cost.
4. **`cpufreq` genuinely absent on metal**, and `cpufv_disabled=1` — the driver deliberately
   blocks FSB control on model "701".

## 5. THE OPEN PROBLEM — the 701 will not boot after a reboot

### What was done
`ssd-boot.sh --auto` ran to completion on the live machine (`rc=0`, ~11 min) and **verified**:
- `sda1` → `EEEPCBOOT` ext4, boot UUID `a86df628-29df-46d2-8ca6-8e48c88069e9`
- SSD `/boot` got `vmlinuz-6.12.112-eeepc`, `initrd.img-rescue`, `grub/grub.cfg`
- GRUB installed to the SSD MBR (`55 aa`)
- **At verify time the SD was unchanged**: root still `/dev/sdb1`, its own `/boot` intact, its
  `grub.cfg` still pointing at its own UUID `b0057a11-…`

Then `systemctl reboot` was issued. **The machine did not come back** — a full `/24` sweep found
21 live hosts and none was the 701. It is not merely on a new IP.

### Prime suspect (own it)
**Step 3 of the script ran `update-initramfs -c -k 6.12.112-eeepc`.** Because `/boot` is still the
SD's at that point, this **regenerated the live card's own `/boot/initrd.img-6.12.112-eeepc`**
(observed post-run: `33122243` bytes, timestamped `23:16`). So the script *did* modify the live
boot files although `/boot` was only ever *copied* to the SSD. If that regenerated initramfs is
bad, the card fails to boot exactly as observed.

**This is now fixed in the source** (`v1.3.0`): step 3 is read-only — the rescue behaviour comes
from `break=mount` on the kernel cmdline, so there is nothing to regenerate; the script just keeps
a spare copy of the existing initrd. The comment in the script explicitly forbids reintroducing
`update-initramfs`.

### Secondary hypotheses (not yet excluded)
- The BIOS now prefers the **SSD** (it became bootable today). If the SSD's GRUB chainloaded but
  the embedded prefix or `search --fs-uuid` failed, it would sit at a `grub>` prompt — which looks
  exactly like "no network".
- A bad interaction between the SSD's GRUB and the SD's, or an MBR/BIOS-boot-order change.

### What has NOT been established
- **Nobody has seen the screen.** Everything above is inference from network silence.
- Whether the machine is at a `grub>` prompt, a GRUB menu, a black screen, or simply powered off.
- Whether the 701 BIOS will boot the CFA/PATA SSD *at all* (still unverified — and exactly why the
  design never depended on it).

## 6. Recovery (the machine's owner is physically present)

1. **Esc at POST** → one-time boot menu → pick the **SD card** (`CardReader`). Does it boot?
2. If not: **F2 → Boot** → put the **SD card** first → save & exit.
3. If a **GRUB menu** appears: try `Deeebian (SSD boot / SD root)`, then the `rescue` entry.
4. If a **`grub>` prompt**: type `ls` and record the output — that alone identifies the device map.
5. If **black screen**: suspect the regenerated initramfs (§5), not the SSD.

Nothing here is unrecoverable: the SD's filesystem was intact at verification, the SSD image is
verified on the Mac (`5f0692cb…`), and the card can simply be re-flashed from the local v1.3.0
checkout. **Worst case is a reflash, not a dead machine.**

## 7. Next steps, in order

1. **Find out what the screen says** (§6). Everything else is guesswork until then.
2. **Recover the machine** — boot the SD, or reflash the card.
3. **Fix the release tagging** (§3) — land the branch on `main` so `tags: ["v*"]` fires, or tag the
   commit the run actually built. Right now the tags are not reproducible.
4. **Rebuild and flash v1.3.0**, then confirm on hardware: the games are present, `battery-rejuv`
   works, `eeepc-thermals`/`eeepc-bench` run, and the **first-boot SSD service** does its job
   unattended (that specific path has never been exercised end-to-end).
5. **Only then** revisit SSD boot, using the fixed read-only script. Add a `--dry-run` gate and
   confirm the SD still boots **before** changing BIOS boot order.
6. **Close PR #1** as superseded (the user approved this; it is stale and merging it would revert
   improvements already in `v1.3.0`).
7. **Root-on-SSD** remains available as a separate, higher-risk project — the SSD is 2× faster, but
   root writes constantly and the flash is unreplaceable. `/boot`-only was chosen deliberately.
